## 1. Introduction

### 1.1 Purpose
This Software Requirements Specification (SRS) defines the complete technical blueprint for **Sentinel: An OSINT Data Pipeline with Multi‑Source Consensus Scoring and LLM Consistency Verification**. It serves as the single source of truth for **specification‑driven development** across both the Proof of Concept (PoC) and the production‑ready Final Year Project (FYP). All implementation decisions—from database schema to microservice boundaries—must reference this document.

### 1.2 Scope
Sentinel is heavily inspired by the core mechanisms of **World Monitor (https://www.worldmonitor.app)**. It ingests global event data from the **GDELT 2.0** project, filters military‑relevant events, and applies **Geographic Convergence Detection** to cluster them spatio‑temporally into "Convergence Zones" (Hotspots). 

It computes a **Consensus Confidence Score** based on source density and geopolitical diversity. Finally, it leverages an **LLM (Llama‑3‑70B via NVIDIA NIM)** to verify information consistency and generate a strictly source‑attributed Situation Report (SITREP) known as an "AI Intelligence Brief".

The system includes:
- A Python‑based data pipeline.
- PostgreSQL + PostGIS for persistent storage and spatial queries (from Day 1 of PoC).
- A Streamlit dashboard (PoC) → React/Next.js + dual map engine (globe.gl + deck.gl + MapLibre GL) in production, matching World Monitor’s implementation.
- FastAPI microservices for production scalability.


### 1.3 Definitions & Acronyms

| Term | Definition |
|------|------------|

| CAMEO | Conflict and Mediation Event Observations (event taxonomy) |

| HDBSCAN | Hierarchical DBSCAN (adaptive density clustering) |

## 2. Overall Description

### 2.1 Product Perspective
Sentinel is a standalone, automated OSINT enrichment pipeline. It fits into the broader military intelligence workflow as a **watch‑centre augmentation tool**, providing analysts with near‑real‑time validated event summaries. The system does not replace human judgment but shortens the time from raw event to verified insight.

### 2.2 User Characteristics

- **PoC Phase:** Academic supervisor, examiners, and the developer himself. Single‑user Streamlit dashboard.
- **Production Phase:** Multiple analysts (read‑only), an admin user (configuration). Authentication via JWT.

### 2.3 Constraints

- GDELT 2.0 updates every 15 minutes; the pipeline must stay in sync.
- NVIDIA NIM API may impose rate limits; PoC budget is limited by free tier credits.
- PoC hardware: single developer machine with 16 GB RAM; production target is a cloud VM with 4 vCPUs, 8 GB RAM.
- PostgreSQL + PostGIS must be used from Sprint 1 to eliminate migration risk.

### 2.4 Assumptions

- Internet connectivity is continuous.
- GDELT 2.0 data format remains stable.
- LLM responses are deterministic enough for evaluation (temperature = 0).

## 3. System Architecture

### 3.1 High‑Level Architecture

Sentinel follows a **pipeline‑based microservices architecture** in production, but a monolithic Python process during PoC to reduce complexity.

| Layer | Component | Technology (PoC) | Technology (Production) |
|-------|-----------|------------------|--------------------------|
| Ingestion | GDELT Fetcher & Filter | Python (`requests`, `pandas`) | same, containerized |
| Storage | Events, Sources, Hotspots, Summaries | PostgreSQL 15 + PostGIS (Docker) | Managed PostgreSQL + PgBouncer |
| Processing | Clustering Engine | Python, scikit‑learn | same, stateless worker |
| AI Services | LLM Verifier | Python + NVIDIA NIM API | same, async with `httpx` |
| API Gateway | – | Streamlit direct DB access | FastAPI REST + SSE |
| Frontend | Dashboard | Streamlit + pydeck (Deck.gl) | Next.js + globe.gl + deck.gl + MapLibre GL |
| Message Bus | – | Not needed (synchronous) | Redis Streams / RabbitMQ |

## 4. Functional Requirements

### 4.1 Ingestion & Filtering

**FR‑1‑GDELT_FETCH**  
The system shall fetch the latest GDELT 2.0 export CSV every 15 minutes using the `lastupdate.txt` index.  
**Input:** URL from `http://data.gdeltproject.org/gdeltv2/lastupdate.txt`.  
**Output:** A `pandas.DataFrame` containing all columns.  
**Acceptance Criteria:**  
☑ The full CSV is downloaded within 30 seconds (timeout = 30 s).  
☑ On network failure, retries are attempted up to 3 times with exponential backoff.

**FR‑2‑CAMEO_FILTER**  
The system shall retain only rows where `EventRootCode` is between 14 and 19 (inclusive), covering “Use of conventional military force”.  
**Acceptance Criteria:**  
☑ A synthetic CSV with 100 mixed events is filtered correctly: only military rows remain.  
☑ Events with missing `EventRootCode` are discarded.

**FR‑3‑DEDUP_STORAGE**  
The system shall insert events into the `events` table using `INSERT ... ON CONFLICT (gdelt_global_event_id) DO NOTHING` to guarantee idempotency.  
**Acceptance Criteria:**  
☑ After two consecutive identical fetches, `events` row count remains unchanged.  
☑ The `point_geom` column is populated as `ST_SetSRID(ST_MakePoint(lon, lat), 4326)` for every valid coordinate pair.

### 4.2 Spatio‑Temporal Clustering
*Architecture Note: This module implements the "Geographic Convergence Detection" logic as described in the World Monitor Documentation. It transforms unstructured noise into actionable geographic hotspots.*


**FR‑4‑CLUSTER_WINDOW**  
The clustering module shall retrieve all events from the current UTC time minus a configurable **look‑back window** (default 2 hours), supplemented by the newest ingestion batch.  
**Acceptance Criteria:**  
☑ No future or duplicate events are included.

**FR‑5‑DBSCAN_CLUSTER**  
The system shall group events using DBSCAN (or HDBSCAN) with a Haversine distance metric and a temporal penalty function.  
`eps` (spatial) = **50 km** (configurable), `min_samples` = **3**.  
Temporal penalty: two events more than **1 hour apart** are assigned infinite distance, preventing cross‑window clustering.  
**Acceptance Criteria:**  
☑ Two events 10 km and 30 min apart are clustered; two events 60 km apart are separated.  
☑ Noise points are registered in `events` but not included in any hotspot.

**FR‑6‑HOTSPOT_STORAGE**  
Each cluster shall be stored in the `hotspots` table with:  
- `centroid_geom` computed as the mean of member coordinates.  
- `radius_km` = maximum Haversine distance from centroid to any member.  
- `start_window` and `end_window` = min/max `event_date`.  
- `event_count`, `unique_sources`.  
A many‑to‑many link table `event_hotspot` shall associate events to their cluster.  
**Acceptance Criteria:**  
☑ After clustering, `SELECT COUNT(*) FROM hotspots` > 0 for a high‑density real dataset (e.g., Ukraine).  
☑ Every non‑noise event appears in exactly one hotspot.

### 4.3 Consensus Scoring

**FR‑7‑SOURCE_DENSITY**  
For each hotspot, compute `source_density = tanh( n_unique_domains / 10 )`, where `n_unique_domains` is the number of distinct source domains among member events.  
**Acceptance Criteria:**  
☑ With 20 unique domains, `source_density ≈ 0.96`; with 1 domain, `≈ 0.099`.

**FR‑8‑GEOPOLITICAL_DIVERSITY**  
Compute diversity using Shannon entropy over country codes (from `sources` table):  
`diversity = entropy / log2( N )` where N = number of unique countries present.  
**Acceptance Criteria:**  
☑ All events from one country → diversity = 0.  
☑ Events from 4 countries equally → diversity ≈ 1.0.

**FR‑9‑CONFIDENCE_SCORE**  
`conf_score = 0.6 * source_density + 0.4 * geopolitical_diversity` (scaled 0‑100). Store in `hotspots.conf_score`.  
**Acceptance Criteria:**  
☑ A hotspot with high density and low diversity gets ~60; low density and high diversity ~40.

### 4.4 LLM Verification & Summarization

**FR‑10‑THRESHOLD_GATE**  
Only hotspots with `conf_score > 40` (configurable) are sent to the LLM.  
**Acceptance Criteria:**  
☑ No LLM call for a cluster with score 35.

**FR‑11‑PROMPT_GENERATION (Attributed AI Intelligence Briefs)**  
For each qualifying hotspot, construct a prompt containing:  
- List of article headlines, URLs, and source domains.  
- Instruction: "Act as an intelligence analyst. Detect any factual conflicts. Summarise in 3‑4 sentences. **CRITICAL:** You must follow the 'Attributed AI Briefs' methodology. Every single claim in your summary MUST end with a citation bracket containing the index or URL of the source (e.g., 'Forces advanced 5km [1]'). Do not hallucinate."  
- Output JSON: `{conflict_detected: bool, conflict_detail: str, summary: str, sources_cited: [str]}`  
**Acceptance Criteria:**  
☑ Prompt fits within glm-4.7 context window.
☑ If the LLM generates a claim without a `[source]` citation, the validation layer (Pydantic) must flag it or reject it.

**FR‑12‑NIM_API_CALL**  
The system shall POST the prompt to the NVIDIA NIM API endpoint with `temperature=0`, `max_tokens=500`, and retry on `429 Too Many Requests` up to 3 times.  
**Acceptance Criteria:**  
☑ Successful response in < 15 s for 90 % of calls.  
☑ Parsed JSON is stored in `llm_summaries`.

### 4.5 Dashboard (PoC)

**FR‑13‑STREAMLIT_MAP**  
The Streamlit app shall display a pydeck (Deck.gl) map centered on the user’s region, with markers for each hotspot colored by confidence (green >70, yellow 40‑70, grey <40). Clicking a marker shows the SITREP.  
**Acceptance Criteria:**  
☑ Map updates after manual “Refresh” or automated 15‑minute trigger.

## 6. Detailed Design

### 6.1 Component Design

#### 6.1.1 Ingestion Module (`ingestion.py`)
- Class `GDELT2Ingestor`
  - `fetch_latest_url()` → returns CSV URL.
  - `download_csv(url)` → returns `DataFrame`.
  - `filter_military(df)` → returns filtered `DataFrame`.
  - `insert_to_db(df, conn)` → uses `execute_values` with `ON CONFLICT`.
- Dependencies: `requests`, `pandas`, `psycopg2`.

#### 6.1.2 Clustering Engine (`clustering.py`)
- Function `build_distance_matrix(events_df, max_time_diff_h=1)`:  
  Creates a precomputed distance matrix where entry (i,j) = Haversine km if time diff < 1 h else `np.inf`.
- Function `cluster_dbscan(dist_matrix, eps_km=50, min_samples=3)` → returns labels.
- Class `ClusterRepository` to write hotspots and event‑hotspot links.

#### 6.1.3 Consensus Scorer (`scoring.py`)
- `compute_source_density(domains: List[str])` → float.
- `geopolitical_diversity(country_codes: List[str])` → float using `scipy.stats.entropy`.
- `score_hotspot(hotspot_id, db)` → updates `conf_score`.

#### 6.1.4 LLM Verifier (`llm_verifier.py`)
- Function `build_prompt(hotspot_data: dict)` → str.
- Function `call_nim_api(prompt: str)` → dict (parsed JSON) using `requests.post`.
- Class `LLMRepository` to store results.

#### 6.1.5 Frontend (PoC: `app.py`)
- Single file Streamlit application.
- Automatic reload via `st.rerun` inside a `while True` loop with `time.sleep(900)`.

### 6.2 Database Schema (PostgreSQL + PostGIS)


### 6.3 API Specifications (Phase 2 – FastAPI)

| Endpoint | Method | Description | Request | Response |
|----------|--------|-------------|---------|----------|
| `/events` | GET | Query events within a polygon/time | `?sw_lat=&sw_lon=&ne_lat=&ne_lon=&start=&end=` | GeoJSON FeatureCollection |
| `/hotspots` | GET | Latest hotspots with confidence | `?limit=50&min_conf=40` | JSON array of hotspot objects |
| `/hotspots/{id}/summary` | GET | Get SITREP for a hotspot | – | `{summary, conflict_detected, sources_cited}` |
| `/hotspots/stream` | GET (SSE) | Real‑time hotspot updates | – | `data: {hotspot_id, lat, lon, conf_score}\n\n` |

### 6.4 Data Flow – Processing Sequence (Phase 2 Asynchronous)

1. **Ingestion Worker:** Fetch GDELT → filter → insert into DB → publish event IDs to Redis Stream `ingested_events`.
2. **Clustering Worker:** Consume stream, batch events in a sliding window, run DBSCAN, write `hotspots`, publish `hotspot_created` with ID.
3. **Consensus Worker:** Listen to `hotspot_created`, compute confidence, update DB, if score > threshold publish `llm_needed`.
4. **LLM Worker:** Consume `llm_needed`, call NIM API, store summary, publish `summary_ready`.
5. **API Server:** Listen to all streams, push updates to SSE clients.

*(For PoC, these are executed synchronously in a single script: `pipeline.py`.)*
