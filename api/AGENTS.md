# DOX — api/

## Purpose

FastAPI REST + SSE layer: hotspot and event endpoints, rate limiting, Prometheus metrics, and server-sent event streams.

## Ownership

All files in `api/`, including `api/routes/`.

## Local Contracts

- All SQL lives in `api/queries.py` — no inline SQL in route handlers or `sse.py`
- **`alert_level` is derived, never selected** (`_alert_level_sql`, FR-13/FR-WM-CONVERGENCE). Neither `hotspots.alert_level` nor `grid_cells.alert_level` is written by anything — both are NULL on every row (1321 hotspots, 2632 cells, 2026-08-20). The old `COALESCE(h.alert_level,'Medium')` therefore hard-coded the projection, and the filter compared the **raw** column, so `?alert_level=<any value>` matched zero rows — including the `Medium` the same response reported for every hotspot. Projection and filter must use the same expression; a filter on a stored column beside a derived projection is the exact shape of that bug. Thresholds must stay identical to `pipeline/clustering.py:classify_alert_level`, which is authoritative: **2+ distinct event types are required to raise the level at all**. Dropping that check is not a simplification — one event type caps `convergence_score` at 25+25=50, exactly the `High` boundary, so it promotes every single-type cell, and on the current corpus every cell is single-type (max observed score is 50). `classify_alert_level` returns None below Medium; the SQL floors to `'Medium'` to keep `schemas.Hotspot.alert_level` non-null. Guarded by `tests/test_api_alert_level.py` (no DB needed).
- Rate limiting enforced via `ratelimit.py` — do not bypass for any endpoint
- SSE streams are in `api/sse.py` and `api/routes/stream.py`; keep them separate from request/response routes
- SSE generators run on the shared asyncio event loop: every synchronous blocking call inside them (Redis `StreamBus.read`/`ack` with `block=`, pooled DB reads like `_enrich`) MUST be wrapped in `asyncio.to_thread`. A blocking call left on the loop starves all concurrent REST requests — a live stream once hung `/hotspots` for minutes. Covered by `test_sse_read_does_not_block_event_loop`.
- SSE frames MUST serialize through `json.dumps(..., default=_json_default)`. `_enrich` returns a raw `hotspots` row whose `end_window`/`created_at` are `timestamp with time zone` → `datetime`, which plain `json.dumps` cannot encode. That exception escapes mid-yield, so the chunked response ends without its final chunk (browser: `ERR_INCOMPLETE_CHUNKED_ENCODING`) and the `bus.ack` on the following line never runs. Because `StreamBus.read` uses `>` (new entries only), the unacked message is never retried — it strands in the group's pending list while the next emitted event crashes the next connection identically (observed: 218 crashes in 40 min, 18k stranded pending messages, `hotspot_created` never reaching any client). ISO-8601 output matches the `Hotspot` response_model on `GET /hotspots`. Covered by `test_sse_hotspot_created_frame_is_json_serializable`.
- Pydantic schemas in `api/schemas.py` are the API contract — changing field names is a breaking change
- Metrics exported via `api/metrics.py`; add new counters/gauges there, not inline
- `GET /hotspots` and `GET /grid_cells` accept `max_age_hours` (default 720 = 30 days); rows whose `end_window` (hotspots) / `updated_at` (grid_cells) is older are excluded. This is the server-side guard against stale hotspots accumulating in the response window — do not remove it. `max_age_hours=None` in `queries.py` disables the cap (used only by internal callers/tests).
- `fetch_hotspot_events` excludes `is_noise` links and must stay in lockstep (filter + ORDER BY + duplicate collapse) with `LLMRepository.fetch_hotspot_articles` and `pipeline.consistency.fetch_hotspot_evidence` — FR-16 citation numbering depends on all three agreeing row-for-row. The collapse itself is `pipeline.citations.collapse_duplicate_urls`; never reimplement it locally.
- `fetch_hotspot_events` rows carry `duplicate_count` (≥ 1) — how many `events` rows shared that URL before the collapse. GDELT emits one row per extracted actor pair, so an uncollapsed list cited one article under several numbers and read as independent corroboration.
- `fetch_hotspot_events` exposes the FR-21 severity columns (`goldstein_scale`, `avg_tone`, `num_sources`, `fatalities`) as nullable passthroughs. They are additive SELECT columns only — the `ORDER BY` and `is_noise` filter must never change, or `citation_index` renumbers and SITREP `[N]` markers desync.
- `fetch_hotspots`, `fetch_hotspot_by_id`, and the search payloads (`_HOTSPOT_SELECT` and the FTS `SearchEvent.hotspot` dict) all carry `start_window`, `end_window`, `created_at`, and `consistency_score` so the detail panel shows hotspot lifespan and consistency whichever way the hotspot was opened; SSE `hotspot_created` frames carry them through `_json_default` as ISO-8601.
- The `/search` events group deduplicates on `(url, hotspot_id)` via `row_number()`, keeping the most recent row and reporting `report_count`. The `LIMIT 10` sits outside the dedupe subquery — limiting first would return fewer than ten distinct articles. Partitioning on `url` alone would be wrong: the same article under two hotspots is two distinct destinations.
- `fetch_hotspot_claims` recomputes `citation_index` from `fetch_hotspot_events` — the lockstep contract now covers claims too
- `GET /hotspots/{id}/claims` follows the standard Bearer + rate-limit pattern (FR-24); the payload now carries `Claim.consensus_weight` (stored since migration 020) plus each claim's `evidence[].relation`/`.probability`/`.domain`, which together with `trust_score` from `GET /hotspots/{id}/events` are what make the published score reconstructible. Since 2026-08-20 `consensus_weight` alone is **not** sufficient: FR-22(d)'s claim value depends on the support/dispute split, not only on status, so a client must recompute both from the evidence rows (`frontend-next/lib/window-consistency.ts` does) and `Claim.origin_domains` (migration 023, **null when NULL** — the client must read NULL as "written before 023, unverifiable", not as an empty origin set)
- `GET /hotspots/{id}/report` (FR-29, `api/routes/report.py`) is the **only user-triggered *LLM* call in the API** — every other LLM call runs inside the pipeline scheduler, never in a request (`/translation` is the other user-triggered *external* call, but it reaches Google Translate, not an LLM). That drives its guards: its own `limit_report` bucket (`SENTINEL_REPORT_RATE_PER_MIN`, default 4 — the shared 60/min bucket in front of an LLM is a cost and DoS hole), a single LLM attempt with `retries=1` and `SENTINEL_REPORT_TIMEOUT_S` (default 30 — the pipeline default of 3-plus-Ollama-fallback can hold a worker for minutes, and an outer retry at temperature 0 would re-send a byte-identical prompt), and a Redis cache keyed on `(hotspot_id, from, to, the window's full event_id set)` so an unchanged report is never regenerated and a changed one — including one that *lost* events without changing the max id — is never served stale. **Ollama-only hosts work**: `call_llm_raw` skips the NIM call entirely when `NVIDIA_NIM_ENDPOINT` is empty (a POST to `""` raises MissingSchema, which the 429/5xx retry branches never catch, so the fallback was unreachable). The route reuses one Redis client with a 1s connect timeout rather than a fresh pool per request, and treats a naive `from`/`to` (no offset) as UTC — `events.event_date` is timestamptz, so an offset-naive comparison would TypeError (unhandled 500) instead of a clean 4xx. It returns **503** when no NIM/Ollama credentials are configured and **422** on citation-validation failure (`validate_citations`, FR-11/FR-12) — an uncited narrative must never ship. Window bounds are validated (422) **before** the DB lookup. `fetch_hotspot_name` (`api/queries.py`) is the single-hotspot name accessor; existence is determined by `fetch_hotspot_events` returning None
- `GET /hotspots/{id}/translation` (FR-30, `api/routes/translate.py`) serves a Vietnamese display translation of the SITREP and claims via Google Cloud Translation v2 — the only externally-billed call in the API, which is why it needs its own `limit_translate` bucket (`SENTINEL_TRANSLATE_RATE_PER_MIN`, default 20): the report's 4/min would 429 an analyst clicking through five hotspots, and the shared 60/min in front of a metered API is the same cost hole `/report` exists to avoid. Reads come only from `fetch_hotspot_summary` and `fetch_hotspot_claims`, unchanged; nothing is written to Postgres and no scoring path reads its output. The Redis cache is keyed on CONTENT (`sha256(lang + hotspot_id + summary + claim_id:claim_text pairs)`), not ids, because the pipeline rewrites `claims` every tick — an id-keyed entry would serve the previous run's text under new claims. Citation markers are protected through `<span translate="no">` + `format: "html"` and guarded after the call: a changed marker multiset returns the English summary with `summary_translated: false` (a mistranslated citation is worse than untranslated text). 404 when `fetch_hotspot_summary` is None; 422 for any `lang` other than `vi`; 503 without `GOOGLE_TRANSLATE_API_KEY` or on a Google failure; 200 with an empty payload and no upstream call when there is neither summary nor claims. The key is server-side only — it must never appear in a `NEXT_PUBLIC_*` variable.
- `fetch_hotspots`, `fetch_hotspot_by_id`, and `_HOTSPOT_SELECT` carry `source_density`, `geopolitical_diversity`, `convergence_types` and `convergence_events` so the detail panel can show *why* a score is what it is. The two convergence inputs **must resolve from the same row the published `convergence_score` came from** — inputs from a different row would draw a bar that does not add up. That is a `CASE WHEN g.convergence_score IS NOT NULL THEN <grid_cells inputs> ELSE <hotspots inputs> END` per input, NOT per-column `COALESCE`: a grid_cells row with a NULL score would otherwise leak its `event_type_count`/`total_events` into the inputs while the score fell through to `hotspots.convergence_score`. `convergence_score` is emitted **nullable** (`COALESCE(g.convergence_score, h.convergence_score)`, no `, 0`) — a NULL means the hotspot never went through grid-cell convergence, and flattening it to 0 would make the client draw a hollow bar instead of "not yet scored" (hotspots 8/9 in the live DB have NULL score and cell_id). `fetch_hotspot_summary` emits it nullable too (`HotspotSummary.convergence_score: float | None`), so the summary endpoint never reports 0 for a hotspot `/hotspots` reports null for. The `WHERE min_convergence` clause keeps its own `COALESCE(..., 0)` because a filter needs a non-null comparison. Covered by `test_convergence_inputs_reconstruct_the_published_score` (skips NULL scores), `test_convergence_inputs_follow_the_score_row`, and `test_api_score_breakdown`'s nullable path.
- `fetch_hotspot_events` also selects `s.country_code` (additive column only — the `ORDER BY` and `is_noise` filter are unchanged, per the citation-lockstep contract above).
- Credential endpoints use `limit_auth` (`AUTH_RATE_PER_MIN = 10`), a **separate** `TokenBucket` from the shared 60/min `_bucket` behind `limit_events`/`limit_hotspots`. Putting login on the shared bucket would let login attempts spend the budget the dashboard needs, and 60 password guesses per minute per IP is not a throttle. The dependency runs before the handler, so an over-budget request never takes a pooled connection. Both limiters key on the real client IP: `_client_ip(request)` reads the **last** `X-Forwarded-For` entry when the direct socket peer is in `SENTINEL_TRUSTED_PROXIES` (comma-separated env; the Compose reverse proxy), else falls back to the socket peer. Without this, every user behind the Compose proxy shares one bucket and the 10/min auth throttle locks out the whole site — X-Forwarded-For is only honored from a trusted peer because the immediate client can forge it. Covered by `tests/test_ratelimit.py::test_client_ip_*`.
- `GET/POST/DELETE /auth/users` are admin-only (`require_role("admin")`) — **there is no public registration endpoint**, by product decision. `fetch_users` never selects `password_hash` and `schemas.UserRow` would drop it anyway. `insert_user` uses `ON CONFLICT (username) DO NOTHING ... RETURNING` so a duplicate is a 409 without a SELECT/INSERT race or an aborted transaction. `CreateUserRequest` caps the password at **72 bytes** because bcrypt silently truncates there — a longer password would authenticate against its own prefix. `DELETE` refuses self-deletion (route-side; not racy) and refuses the last admin, but the last-admin check lives **inside the DELETE statement itself** (`DELETE_USER_SQL` in `delete_user`). The count subquery **locks the admin rows with `FOR UPDATE`** — a plain `SELECT count(*)` is write-skewed under READ COMMITTED: two concurrent deletes of *different* admin rows both evaluate the count against their own pre-commit snapshot (no row-lock conflict, no EvalPlanQual re-check) and both succeed, leaving zero admins. The lock makes the second delete block and re-count after the first commits; the blocked delete returns `rowcount 0`. The route re-fetches the row to tell the two `rowcount 0` causes apart: if the target vanished concurrently between the route's first fetch and the delete it returns 404, if it still exists the last-admin guard blocked it and it returns 400. A separate `count_admins` SELECT before the DELETE is TOCTOU for the same reason. Covered by `test_last_admin_guard_holds_under_concurrent_deletes` (raw psycopg2 connections on a barrier — the `TestClient`-based version serializes every request and cannot fail), `test_delete_vanished_user_is_404`, and `test_delete_user_returns_false_for_a_row_that_vanished_concurrently`. Both this test and `test_cannot_delete_the_last_admin` snapshot/restore the admins they delete so the seeded `admin` login survives the run.

## Work Guidance

- New endpoints go in `api/routes/` as separate files; register them in `api/app.py`
- Use `api/queries.py` for all DB reads; the API layer must not write to the DB
- Test all new endpoints with corresponding tests in `tests/test_api_*.py`
